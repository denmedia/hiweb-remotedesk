# HiWeb RemoteDesk

Android-клиент удалённого рабочего стола (RDP) для планшета Samsung Tab S9 Ultra с чехлом-клавиатурой
и тачпадом и для смартфона (проверяется на Samsung SM-S916B: 1080×2340, 450 dpi ≈ 384 dp в книжной
ориентации), плюс агент для Windows (HiWeb Agent). Пользователь общается по-русски.

## Устройство

- **`README.md`** — презентация приложения для читателя (что умеет, как начать), внизу краткая
  техническая документация. Держать в согласии с кодом: возможности, порты, команды сборки. Глубокие
  детали — по-прежнему здесь и в `windows-agent/PROTOCOL.md`.
- **RDP-клиент написан с нуля на Kotlin**, без FreeRDP/NDK (готовой сборки FreeRDP для Android нет).
  Всё в `app/src/main/java/com/hiweb/hiwebremotedesk/rdp/`:
  - `RdpClient.kt` — X.224 → TLS → CredSSP/NTLM (`CredSsp.kt`, `Ntlm.kt`) → MCS → возможности → графика;
    статические каналы и их нарезка на фрагменты по 1600 байт.
  - Каналы: `ClipboardChannel` (cliprdr, текст и файлы), `DriveChannel` (rdpdr: диски, несколько
    устройств, `attach/detach`), `SoundChannel` (rdpsnd), `AudinChannel` (DVC `AUDIO_INPUT`, MS-RDPEAI:
    микрофон планшета на ПК; только PCM 16 бит, передача включается `RdpClient.setMicrophone`),
    `EcamChannel.kt` (`EcamEnumerator` + `EcamDevice` + `EcamShared`, DVC `RDCamera_Device_Enumerator` и каналы
    устройств с придуманными именами `Camera0`, `Camera1`…, MS-RDPECAM: камеры планшета в программах Windows;
    MJPG или NV12, кадр отдаётся ровно на `SampleRequest` сервера), `DynamicChannel` (drdynvc; фрагментация
    DATA_FIRST, `DvcHandler`; `factories` — отдельный обработчик на каждое открытие канала с тем же именем), `MouseCursorChannel` (DVC курсора), `DisplayControlChannel` (RDPEDISP:
    смена размера стола без переподключения, только вместе с GFX — сервер отвечает ResetGraphics),
    `GfxChannel` + `Zgfx` + `RfxProgressive` (RDPEGFX, нужен GNOME Remote Desktop).
  - Байтовые структуры — `Bytes.kt` (`ByteWriter`/`ByteReader`). Раскладки PDU брались из исходников FreeRDP.
- **Экран сеанса** — `RemoteActivity.kt` (Compose-оболочка, панель инструментов, баннеры, жизненный цикл)
  и `RemoteView.kt` (отрисовка, касания). Экран сеанса поворачивается (`fullUser`, учитывает блокировку
  поворота): в книжной ориентации стол 1920 по высоте. При повороте с GFX — `RdpClient.resizeDesktop`,
  без GFX (Windows) — переподключение с новым размером (сеанс Windows сохраняется; события старого клиента
  отсекаются по `sessionSeq`). Кнопка «Повернуть» в панели сеанса (`rotateSession`, логика направлений и часы анимации — `SessionRotation.kt`) фиксирует `requestedOrientation`: из альбомной картинка идёт на 90° влево (поворот дисплея −1), из книжной обратно; работает при выключенном автоповороте, после возврата в альбомную при включённом автоповороте ориентация отдаётся системе. Смена ориентации (любая, не только кнопкой) показывается анимацией в `RemoteView`: `beginRotation` (из `onConfigurationChanged`) снимает картинку стола, она поворачивается и растягивается под новое окно, мутнеет (`RenderNode` + `RenderEffect`) и держится, пока Windows не ответит новым размером (`initDesktop` заливает новый стол прежней картинкой, готовность — по покрытию кадрами, иначе по таймауту), затем плавно исчезает; системная анимация поворота отключена (`ROTATION_ANIMATION_JUMPCUT`), переподключение без GFX идёт без окна «Подключение…» (`quietReconnect`). Прежняя картинка уходит, когда кадры нового стола покрыли половину площади и замолчали на 0,5 с (экран входа и «Добро пожаловать» после переподключения анимируются и ждут своего конца; не дольше 5 с после первого кадра), живой стол рисуется только под исчезающей картинкой; `settleOrientation(afterReady = true)` не завершает анимацию (размер после переподключения совпадает с запрошенным). Пока Windows отвечает, поверх картинки крутится лоадер (`RemoteView.onRotationWait` → `rotationWait`). Угол старта — кратчайший путь (поворот дисплея на 3 = −1 четверть). Кнопка «Настройки» в панели сеанса открывает `SessionSettings`: только то, что
  действует на лету (сила скролла/инерции, скорость мыши и её колёсика (`Device.mouseWheelLevel`, множитель на
  `AXIS_VSCROLL` в `RemoteView.mouseWheel`) — `applyInputLevels`, сохраняются через
  `DeviceRepository.update`, который не пишет сеансовые пароли; все четыре ползунка — проценты 50–200 с шагом 10
  (`Device.*Percent`, `StrengthLevels.snap`); «100%» у инерции и мыши — настроенные значения владельца
  (`StrengthLevels.inertiaFactor`/`mouseFactor`, в движок идёт именно они, а не `factor`), при смене опорной
  величины поднять `SCALE_VERSION` и добавить шаг в `DeviceRepository.migrateLevels` (старые уровни 1–9 → проценты); захват жестов; микрофон; кнопки «Калибровка», «Файлы на ПК», «Папка на ПК» — их нет в панели сеанса) — новую живую настройку
  добавлять туда, а требующую переподключения (масштаб, глубина цвета, диск) остаётся в форме ПК. Масштаб Windows
  (`Device.scalePercent`, Client Core Data и DisplayControl) сервер применяет только к новому сеансу: к сохранённому
  сеансу пользователя (один на пользователя, создан на физическом мониторе) подключение масштаб не меняет — проверено на
  ПК, DisplayControl с тем же размером тоже не помогает; в форме ПК это сказано в подсказке. Выход из сеанса
  (`leaveSession`) при `isTaskRoot` (сеанс открыт с ПК или из уведомления) сперва открывает `MainActivity`, иначе
  `finish()` сворачивал бы приложение; закрывать экран сеанса через `finish()` напрямую не надо. Windows без GFX по DisplayControl меняет размер у себя, но не сообщает его клиенту. Ввод: `TouchpadEngine` (захват указателя), `TouchpadGestures`,
  `TouchscreenGestures`, `ScrollFling`, `KeyCaptureService` (служба спец. возможностей для Win/Alt+Tab).
  Смартфон: захват указателя и калибровка тачпада не включаются (нет чехла-тачпада —
  `RemoteActivity.fingerInput()` по `smallestScreenWidthDp < 600`), панель сеанса — снизу двумя
  прокручиваемыми строками (`PhoneSessionPanel`) с кнопкой «Клавиатура»; ширина плашек считается
  `panelWidth(phone, …)`, а не фиксированными 520/560 dp. Экранная клавиатура: у `RemoteView` нет
  `InputConnection`, поэтому крошечный `EditText` (`ensureImeEdit`) в окне поднимает системную клавиатуру,
  а её `KeyEvent` разбирает `forwardImeKey` (символы — скан-кодом через `ScanCodes.forChar` либо
  Unicode-событиями RDP, модификаторы держатся вручную); служба перехвата клавиш вызывает тот же
  `handleKeyEvent`. Кнопки мыши «средняя», «назад», «вперёд» Samsung обрабатывает на уровне ОС по своим настройкам
  (`Settings.System mouse_middle_button_option`, в `dumpsys input` — `Mouse button behavior(S/T/B/F)`) и может отдать как
  Home/«Недавние», Back, Forward: приложение сворачивается или сеанс закрывается. `RemoteActivity.mouseButtonAsKey` узнаёт
  такое событие (скан-код BTN_MIDDLE/SIDE/EXTRA/FORWARD/BACK 0x112–0x116 или клавиша без скан-кода от источника «мышь»)
  и шлёт на ПК кнопку через `RemoteView.mouseButtonKey`: средняя — `PTR_MIDDLE`, «назад»/«вперёд» — боковые кнопки
  `RdpClient.sendMouseX` (TS_POINTERX_EVENT, `PTRX_BACK`/`PTRX_FORWARD`; те же кнопки из `MotionEvent.buttonState` идут
  через `applyButtons`). Перехват работает только через службу перехвата клавиш; события пишутся в журнал `Input`.
  На планшете эти кнопки дополнительно доходят до приложения обычными событиями мыши (`buttonState`), а ОС всё равно
  выполняет своё действие (сворачивает, «назад») — его перехватом не отменить. Отключаются они только настройками Samsung
  в `Settings.System`: `mouse_middle_button_option` = 3 (обычный щелчок), `mouse_additional_1_option` и
  `mouse_additional_2_option` = 0 (нет действия); без записи у боковых действует системное «назад»/«вперёд». Приложение
  записать эти ключи не может (провайдер настроек отвечает `IllegalArgumentException: You cannot keep your settings in the
  secure settings` даже при `WRITE_SETTINGS`; пишет только оболочка adb: `settings put system <ключ> <значение>`), поэтому
  пункт «Кнопки мыши» в окне прав (`AppPermission.MOUSE_BUTTONS`, только Samsung) лишь читает их и показывает шаги ручной
  настройки (`howTo`).
  Курсор при захваченном указателе рисуется самим `RemoteView`; если последним вводом был палец
  на экране (`fingerInput`), он скрыт и показывается только при долгом касании и перетаскивании (`fingerCursorShown`);
  ввод тачпадом/мышью (`pointerInput`) возвращает его.
- **Данные** — `data/`: `Device` + `DeviceRepository` (настройки каждого ПК, пароли через `SecretBox`),
  `Network.kt` (определение ОС), `LinuxSsh.kt` (питание Ubuntu по SSH), SAF-диск.
- **UI списка устройств** — `ui/` (`HomeScreen`, `Dialogs`, `HomeViewModel`, `Components`, `Adaptive.kt`).
  Адаптивность по ширине окна (`CompactMaxWidth = 600.dp`): уже 600 dp (смартфон в книжной ориентации) —
  верхняя панель с поиском в меню, фильтры строкой `FilterChips`, одна колонка карточек, кнопки
  «Добавить»/«Найти в сети» — FAB поверх списка; в карточке питание уходит в меню «⋮»
  (`DeviceCard(compact = true)`), а не в ряд из пяти подписанных кнопок. На планшете остаётся боковая панель 320 dp.
  Правило списка ПК: кнопки на карточке не прячутся, а становятся неактивными, пока действие недоступно (сон и гибернация
  — только когда агент на связи и режим есть в `GetPwrCapabilities`; щит защиты виден у всех Windows, активен с данными агента).
  Нажатие на неактивную кнопку открывает окно «что не так и что сделать» (`ui/ButtonHints.kt`, чистые тексты под тестами);
  новую кнопку с условием доступности добавлять сразу с подсказкой.
  Права приложения: кнопка «Права» в верхней панели (на телефоне — пункт меню «⋮») открывает `ui/PermissionsDialog`
  (название, описание мелким шрифтом, справа значок «выдано / не выдано», у невыданных — кнопка запроса или перехода в
  системные настройки; список и проверки — `data/AppPermissions.kt`, enum `AppPermission`). Новое право, которое
  приложение просит у системы, добавлять в этот enum. Для права, которое включается только вручную в настройках
  (`AppPermission.howTo`, сейчас служба «Передача клавиш»), перед переходом показывается окно с шагами. Прямая ссылка на
  страницу службы (`ACCESSIBILITY_DETAILS_SETTINGS`) сторонним приложениям закрыта (право `signature|installer`), поэтому
  открывается общий список с аргументом подсветки `:settings:fragment_args_key` (в чистом Android пункт подсвечивается).
  Форма устройства (`DeviceEditDialog`) разбита на вкладки `EditTab`: «Подключение», «Экран и ввод», «Устройства»
  (микрофон и камера, только Windows), «Файлы»; новая настройка идёт на подходящую вкладку, ошибки проверки
  подсвечивают вкладку красным и при сохранении переключают на неё.
- **HiWeb Agent** (Windows): исходники `windows-agent/` (C# 5), протокол `windows-agent/PROTOCOL.md`.
  Связь — DVC `HiWeb::Agent` (JSON). Android-сторона — `agent/`: `AgentLink` (канал), `AgentInstaller`
  (установка через временный диск `\\tsclient\HiWeb` + Win+R), `PcNotifications`, `SwitchListenerService`
  и `SwitchCommand` (UDP 47853: «switch» — переключиться на планшет, «where» — агент ищет планшет; HMAC).
  `SessionService` держит сеанс в свёрнутом приложении.
  Иконка агента — ноутбук: `windows-agent/app.ico` (иконка exe) и `laptop.png` (вшит ресурсом
  `HiWebAgent.laptop.png`); значок в трее (`TrayIcons` в `Support.cs`) — серый силуэт ноутбука под тему
  панели задач (`SystemUsesLightTheme`: на тёмной светлый, на светлой тёмный; перерисовка по
  `UserPreferenceChanged`), экран и тачпад вырезаны, на экране — батарейка с зарядом планшета (серый контур,
  цветная заливка по уровню, молния при зарядке); без планшета силуэт полупрозрачный. Если меняется картинка,
  пересчитать в `TrayIcons` долю белого экрана (`SCREEN_*`) и проверить пороги вырезания в `Mask`.
- **Связь агента с планшетом без RDP**: агент (`LanLink.cs`) сам подключается к планшету по TCP 47853
  (исходящее соединение — брандмауэр Windows не мешает), рукопожатие и подписанные строки — `SecureLines`
  (C# и Kotlin). На планшете сервер — `AgentHub` (запускает `SwitchListenerService`), он публикует
  `presence` для экрана списка ПК: карточка ПК с агентом на связи показывает кнопки питания
  (`AgentPower`: выключить, перезагрузить, сон, гибернация — только доступные по `Power.cs`/GetPwrCapabilities).
  Без агента остаются прежние кнопки питания через сеанс RDP (`PowerKeys`) или SSH для Ubuntu.
  Превью ПК без сеанса: агент (`ScreenShot.cs`) раз в 15 мин шлёт по LAN `screen` — JPEG экрана, зашифрованный
  `SecureLines.Encrypt` (AES); `AgentHub` расшифровывает и кладёт в `ThumbnailStore.saveJpeg`.
- **Состояние ПК и пробуждение**: агент (`PcStatus.cs`) шлёт `status` (блокировка, кто в сеансе, простой, уход в
  сон/гибернацию/выключение/перезагрузку/выход, MAC для WoL) и по LAN, и по DVC. Планшет хранит последнее
  сообщение (`data/PcStateStore.kt`), состояние карточки выводит `PcStatusRules` (`data/PcStatus.kt`) из него,
  связи с агентом и проверки порта RDP. Подключение к недоступному ПК с известным MAC (`Device.wakeMac`) сначала
  будит его (`data/WakeOnLan.kt`: UDP 9 и 7 на 255.255.255.255, широковещательные адреса подсетей и адрес ПК),
  затем ждёт порт RDP (`RemoteActivity.connectWaking`).
- **Микрофон планшета в сеансе Windows**: настройка `Device.microphone` (по умолчанию выключена) плюс кнопка
  «Микрофон» в меню сеанса; разрешение `RECORD_AUDIO` спрашивается при первом включении. Захват — `MicSource.kt`
  (`AudioRecord`, 16 бит, 40 мс блоки), протокол — `rdp/AudinChannel.kt` (DVC `AUDIO_INPUT`, MS-RDPEAI: версия 2,
  только PCM 16 бит из списка сервера, `DATA_INCOMING` перед каждым `DATA`). Client Info шлёт `INFO_AUDIOCAPTURE`
  (0x200000), иначе Windows не создаёт устройство записи. Windows открывает канал `AUDIO_INPUT` только на время
  записи в программе на ПК, поэтому включение микрофона «взводится» (`RdpClient.micArmed`) и срабатывает на очередной
  OPEN; при включённой настройке и выданном разрешении микрофон взводится сам при старте сеанса, кнопка его выключает.
  При закрытии сеанса захват останавливается. Для Ubuntu канал не включается.
- **Камера планшета в программах Windows**: настройка `Device.camera` (по умолчанию выключена, диалог
  в `ui/Dialogs.kt`); разрешение `CAMERA` спрашивается один раз при входе в сеанс, если настройка включена —
  канал объявляется только при подключении, поэтому разрешение, выданное во время сеанса, требует
  переподключения (`RemoteActivity.askCameraPermission`/`requestCamera`). Захват — `CameraSource.kt`
  (Camera2; `YUV_420_888` → NV12, для MJPG сжатие в JPEG через `YuvImage`). Каждый объектив — **отдельное устройство
  Windows** («Планшет: тыльная», «… (ультраширокая)», «… (телеобъектив)», «Планшет: фронтальная»…): переключение
  делается средствами программы на ПК (кнопка «Сменить камеру», список камер в браузере/Teams). Тип объектива —
  по эквиваленту фокусного расстояния (≤20 мм ультраширокий, >45 мм теле), одинаковые дубли стороны отбрасываются,
  датчики глубины и ИК отфильтрованы по `BACKWARD_COMPATIBLE`; логическая камера с зумом ≤0.7× даёт ультраширокий
  как зум до минимума. Поворот кадра: базовый по формуле Camera2 для альбомного положения планшета
  (`CameraSource.DISPLAY_ROTATION` = 270°: тыльная `SENSOR − 270`, фронтальная `SENSOR + 270`; на Tab S9 Ultra у всех 180°)
  плюс дополнительный из настроек ПК (`Device.cameraRotation`, кнопки 0/90/180/270° по часовой стрелке); при итоговых 90/270°
  снимается альбомный кадр, поворачивается (`Nv12.rotate`) и Windows предлагается книжный 720×1280 (`EcamCamera.rotation`).
  Какие камеры показывать Windows — `Device.cameraOff` (идентификаторы из `CameraSource.catalog()`; отключённые не
  попадают в `devices()`); обе настройки лежат на вкладке «Устройства» формы ПК (значения по умолчанию) и дублируются в окне настроек сеанса: там и кнопка «Камера» в меню
  сеанса меняют набор камер на лету (`CameraSource.configure` + `RdpClient.refreshCameras` → `EcamEnumerator.refresh` шлёт Windows
  `DeviceAddedNotification`/`DeviceRemovedNotification`; каналы устройств названы по номеру в `catalog()`, поэтому имена не сдвигаются).
  Живое добавление/удаление устройств проверено только юнит-тестами; поворот применяется, когда программа на ПК заново откроет камеру.
  Одновременно снимает одна камера, `stop(id)` гасит только свою. Протокол —
  `rdp/EcamChannel.kt` (`EcamEnumerator` на DVC `RDCamera_Device_Enumerator` анонсирует все камеры, затем `EcamDevice`
  на каналах `Camera<i>`; MS-RDPECAM версия 2, объявляется один формат — MJPG 1280×720 с флагом DecodingRequired
  (проверено на ПК только с ним; сырой NV12 и другие размеры на рабочей схеме каналов не пробовались).
  **Windows открывает канал устройства 2–4 раза одновременно** (свойства, запуск потока, запросы кадров): состояние
  потока общее (`EcamShared`), а ответ и кадр уходят в тот канал, откуда пришёл запрос; `Deactivate` с чужого канала
  поток не останавливает. Кадр отдаётся в ответ на `SampleRequest` — лишние кадры не шлются). Поток идёт, только когда программа
  на ПК открыла камеру (`EcamDevice` зовёт `onActive`, `RemoteActivity` показывает значок «Камера: ПК
  смотрит»); сам поток, как у настоящей веб-камеры, запускает приложение на ПК; кнопка «Камера» лишь показывает камеры Windows или убирает их.
  Для Ubuntu канал не включается.
- **Защита RDP** (Windows, агент 1.8+; RDP на ПК может быть открыт в интернет): агент следит за журналами
  Windows, читаемыми без администратора, — `RdpCoreTS/Operational` (событие 140: неверный пароль, с адресом) и
  `TerminalServices-LocalSessionManager/Operational` (21/25 вход, 23 выход, 24 отключение); журнал «Безопасность»
  без администратора недоступен. Файлы агента: `GuardRules.cs` (адреса/подсети `IpTools` и правила `ThreatDetector` —
  чистая логика без интерфейса), `Guard.cs` (`RdpEventSource`, `ConnectionGuard`: история при запуске, журнал и угрозы
  в `%LOCALAPPDATA%\HiWebAgent\guard.json`, команды), `Firewall.cs` (правила брандмауэра), `GuardForm.cs` (окно и
  `GuardText`). Угрозы: `bruteforce` (5 неудач за 10 мин с подсети /24) и `unknown_logon` (вход, после которого планшет
  не открыл канал за 30 с; открыл — адрес запоминается как свой, в истории — по `channel opened` из `agent.log`).
  Блокировка — правило входящего трафика брандмауэра группы «HiWeb Agent»; менять брандмауэр без администратора
  нельзя, поэтому агент запускает свой exe с `--guard-fw …` через `runas` (UAC на ПК, `Program.Main` обрабатывает ключ
  первым делом). Выключенный брандмауэр правил не применяет: на ПК он может быть выключен,
  поэтому блокировка предлагает включить его (`enableFw`, с явным согласием в окне). Android-сторона: `agent/GuardHub`
  (приём `guard_state`/`conn`/`threat`/`guard_result` по LAN из `AgentHub` и из сеанса через `AgentLink`, команды
  `block`/`unblock`/`trust`/`dismiss`), `agent/GuardNotifications` (+ `GuardActionReceiver`: кнопки в уведомлении),
  `data/GuardLog` (чистое слияние и тексты — под юнит-тестами), `data/GuardStore` (хранение по ПК, `GuardNavigation`),
  `ui/GuardDialog` (значок щита на карточке ПК). Протокол — `windows-agent/PROTOCOL.md`.
- **Форма курсора Windows**: сервер по RDP присылает только стрелку (см. память `rdp-cursor`), поэтому агент
  (`CursorWatcher.cs`, сообщение `cursor`: PNG + точка привязки) сам следит за `GetCursorInfo` и шлёт курсор планшету;
  `AgentLink` разбирает его в `CursorImage`, `RemoteView.setAgentCursor` показывает его и не даёт серверной «стрелке
  по умолчанию» его перекрыть. Без агента (и для Ubuntu) остаётся то, что прислал сервер.
- **Сенсорная клавиатура Windows**: планшет шлёт агенту `keyboard` (`physical` — по `Configuration.keyboard`/
  `hardKeyboardHidden` — учитывает и чехол, и Bluetooth; не по списку устройств: `sec_touchpad` чехла виден и без него); без клавиатуры агент
  (`TouchKeyboard.cs`: ловушка мыши + UI Automation + `ITipInvocation`) показывает TabTip при щелчке в поле ввода
  (UIA `Edit`/`Document` с системным курсором; программы с собственной отрисовкой текста — Scintilla/Notepad++ и
  Java AWT/Swing/IDE JetBrains — не отдают ни того, ни другого, поэтому узнаются по классу окна с фокусом,
  `IsSelfDrawnEditor`) и шлёт её прямоугольник (`tkb`); долгое касание внутри него на планшете — автоповтор клавиши, а не правая кнопка.
- **Уведомления Windows → планшет**: `NotificationWatcher.cs` опрашивает `UserNotificationListener` раз в секунду,
  `AgentApp.Forward` шлёт `notif` **только по каналу сеанса RDP** и только при свёрнутом приложении (`ForwardSkipReason`;
  по LAN без сеанса уведомления не идут). Каждое решение пишется в `agent.log` строкой `notif: <приложение> — …`
  (без текста уведомления). Объект слушателя привязан к потоку: опрос берёт свой `UserNotificationListener.Current` в
  своём потоке, иначе `GetAccessStatus` бросает `RPC_E_WRONG_THREAD`. Меню агента «Проверить пересылку уведомлений…»
  (`NotificationCheck.cs`: `NotificationCheckForm` + `ToastProbe`) показывает настоящий тост от имени Windows PowerShell
  и по шагам проверяет доступ, опрос, канал, свёрнутость приложения и ответ планшета `notif_ack` (`PcNotifications.blocker`:
  нет разрешения / выключен канал / приложение на экране). Для `Windows.Data.Xml.Dom` в `build.cmd` подключён `Windows.Data.winmd`.
  Иконка в карточке: агент (`AppIcons.cs`, оболочка `shell:AppsFolder\<AppUserModelId>` + `IShellItemImageFactory`, 128 px,
  только в памяти, вызывать из STA) кладёт PNG в `notif.icon`; планшет (`NotificationIcon.kt`) собирает из него большую иконку
  с цветным значком RemoteDesk в углу, без иконки приложения (системные уведомления) — один значок RemoteDesk. Маленькая
  иконка в статус-баре остаётся `ic_stat_pc`. `GetLogo` из API уведомлений для классических программ возвращает null.

## Сборка и тесты

- JDK нет в PATH: `export JAVA_HOME="/d/Program Files/Android/Android Studio/jbr"` перед `./gradlew.bat`.
- Юнит-тесты и APK: `./gradlew.bat --console=plain -q :app:testDebugUnitTest :app:assembleDebug`.
  В JVM-тестах `android.util.Log` и `org.json` не работают: каналы получают логгер параметром (`log = {}`).
- Агент: `windows-agent\build.cmd` (компилятор C# из .NET Framework 4.8, есть в Windows) → кладёт
  `HiWebAgent.exe` и `version.txt` в `app/src/main/assets/agent/`. Чтобы приложение предложило обновление,
  увеличить `windows-agent/VERSION`, пересобрать агент, затем APK. Только синтаксис C# 5 (без `$""`, `?.`, `=>`-членов).
  Ссылки на UIAutomationClient/Types берутся из `Framework64\v4.0.30319\WPF`.
- Сборка агента не ловит исключения при запуске (однажды `UpdateTray` в конструкторе обратился к ещё не созданному
  `lan` — установка проходила, а процесс падал через секунду). После правок `AgentApp` запускать собранный агент:
  собрать все `src\*.cs` вместе с отдельной точкой входа, которая ловит `UnhandledException`/`ThreadException` и
  закрывает `AgentApp` через 12 с (`-main:`), и убедиться, что исключений нет. Необработанные исключения агента
  пишутся в `agent.log` (`crash:`/`error:`), а падение видно ещё и в журнале Windows (Application, `HiWebAgent.exe`).
- Проверки правил защиты агента (адреса, подсети, обнаружение): `windows-agent\tests\test.cmd` (собирает
  `src\GuardRules.cs` с тестами тем же `csc`; в сборку агента `tests\` не входит). Запускать из PowerShell:
  `& cmd /c ".\test.cmd"` — из Bash `cmd //c` его не находит.
- Репозиторий: https://github.com/denmedia/hiweb-remotedesk (публичный, ветка `main`). Релиз: поднять
  `versionCode`/`versionName`, `:app:assembleRelease`, APK `HiWebRemoteDesk-<версия>.apk` → `gh release create v<версия>`.
  Подпись release — путь к файлу с паролями ключа в `local.properties` (`signing.properties=…`, файл лежит вне репозитория) или `keystore.properties` в корне; пароли не копировать и не коммитить. Без файла release
  неподписан. Release-подпись отличается от debug: поверх debug-сборки на планшете не ставится. R8 выключен.
- **`targetSdk` = 35, не выше.** С Android 16 на экранах ≥600 dp система игнорирует `requestedOrientation` и `screenOrientation` для приложений с `targetSdk` ≥ 36 (проверено на Tab S9 Ultra, SDK 36: при 36 и 37 поворот не меняется даже со свойством `PROPERTY_COMPAT_ALLOW_RESTRICTED_RESIZABILITY`, при 35 — меняется); без этого кнопка «Повернуть» не работает. `compileSdk` может быть выше.
- Python не установлен; для скриптов — node. Большие heredoc в Bash ломаются: скрипт писать файлом.

## Планшет и adb — осторожно

- adb: `%LOCALAPPDATA%\Android\Sdk\platform-tools\adb.exe`, планшет по беспроводному adb.
  Смартфон SM-S916B тоже по беспроводному adb (`adb mdns services` → `adb connect <ip>:<порт>`); при
  перезагрузке телефона или выключенном Wi-Fi он пропадает из списка устройств — тогда проверить `ping`.
- В приложении сохранён **настоящий ПК пользователя**: при открытом сеансе любой ввод через adb уходит на ПК.
  Перед `adb input` и перед `adb install -r` проверять `adb shell dumpsys window | grep mCurrentFocus`;
  если приложение на экране — не трогать, спросить пользователя.
- Не запускать `connectedAndroidTest` (удаляет приложение и сохранённые ПК). Ставить `adb install -r -t`.
- `am force-stop` выключает службу перехвата клавиш (`install -r` её сохраняет).
- Не вводить пароль пользователя самому; учётка Windows блокируется после 10 ошибок за 10 минут.
- **На этом ПК стоит настоящий HiWeb Agent пользователя** (привязан к планшету). Тестовый запуск exe из
  другой папки переустанавливает его; не трогать `HKCU\Software\HiWebAgent\Tablet` и не удалять агент
  без спроса. Команды питания на этом ПК не выполнять (только проверять доступность).
- Не добавлять и не удалять правила брандмауэра на этом ПК и не включать его без спроса (`guard-fw`, `Policy.Rules.Add`,
  `Set-NetFirewallProfile`): это настоящий ПК пользователя, а запрос UAC нельзя подтвердить из
  неинтерактивного сеанса. Читать правила и состояние брандмауэра, журналы Windows и `Get-NetTCPConnection` можно.
  Проверочную обвязку для `ConnectionGuard` собирать в scratchpad с каталогом данных во временной папке, а не в
  `%LOCALAPPDATA%\HiWebAgent` (там настоящие `guard.json` и `agent.log` работающего агента).
