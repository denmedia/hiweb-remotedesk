# HiWeb RemoteDesk

Android-клиент удалённого рабочего стола (RDP) для планшета Samsung Tab S9 Ultra с чехлом-клавиатурой
и тачпадом и для смартфона (проверяется на Samsung SM-S916B: 1080×2340, 450 dpi ≈ 384 dp в книжной
ориентации), плюс агент для Windows (HiWeb Agent). Пользователь общается по-русски.

  как начать), внизу краткая техническая документация; в самом начале каждого — переключатель `English | Русский`, затем заголовок

  возможности, порты, команды сборки — править оба файла сразу. Глубокие детали — по-прежнему здесь и в `windows-agent/PROTOCOL.md`.
- **RDP-клиент написан с нуля на Kotlin**, без FreeRDP/NDK (готовой сборки FreeRDP для Android нет).
  Всё в `app/src/main/java/com/hiweb/hiwebremotedesk/rdp/`:
  - `RdpClient.kt` — X.224 → TLS → CredSSP/NTLM (`CredSsp.kt`, `Ntlm.kt`) → MCS → возможности → графика;
    статические каналы и их нарезка на фрагменты по 1600 байт.
  - Каналы: `ClipboardChannel` (cliprdr, текст и файлы), `DriveChannel` (rdpdr: диски, несколько
    устройств, `attach/detach`), `SoundChannel` (rdpsnd), `AudinChannel` (DVC `AUDIO_INPUT`, MS-RDPEAI:
    микрофон планшета на ПК; передача включается `RdpClient.setMicrophone`). Оба принимают по умолчанию только PCM 16 бит; с
    настройкой `Device.audioCompression` (json `snd_comp`, `RdpConfig.audioCompression`, вкладка «Устройства и файлы»,
    применяется при подключении) — ещё сжатые форматы из `AudioCodecs.kt` (кодеки без `MediaCodec`: IMA ADPCM, MS ADPCM,
    A-law/µ-law; `WaveFormat`, `AudioCodecs.rank` — порядок предпочтения: сжатые идут в ответе клиента выше PCM, потому что
    сервер выбирает формат по номеру из списка клиента). `SoundChannel` разжимает блок до плеера (`AudioSink` по-прежнему
    получает PCM), `AudinChannel` сжимает микрофон кодером на каждый запуск захвата и шлёт целые блоки. AAC/MP3/Opus не
    реализованы. В журнал (тег RDP, `rdpsnd:`/`audin:`) пишется весь список форматов сервера;
    `EcamChannel.kt` (`EcamEnumerator` + `EcamDevice` + `EcamShared`, DVC `RDCamera_Device_Enumerator` и каналы
    устройств с придуманными именами `Camera0`, `Camera1`…, MS-RDPECAM: камеры планшета в программах Windows;
    MJPG или NV12, кадр отдаётся ровно на `SampleRequest` сервера), `DynamicChannel` (drdynvc; фрагментация
    DATA_FIRST, `DvcHandler`; `factories` — отдельный обработчик на каждое открытие канала с тем же именем), `MouseCursorChannel` (DVC курсора), `DisplayControlChannel` (RDPEDISP:
    смена размера стола без переподключения, только вместе с GFX — сервер отвечает ResetGraphics),
    Графический конвейер RDPEGFX: `GfxChannel` (команды, кэш, кадры) + `GfxSurface` (поверхность — ARGB-пиксели в памяти;
    все кодеки и команды рисуют в неё, на экран (`onBitmap`) уходят изменённые области в конце кадра, `EndFrame`; он же
    подтверждает кадр и ждёт ответа аппаратного декодера до `avcWaitMs`) + `Zgfx`. Нужен GNOME Remote Desktop, для Windows
    включается настройкой `Device.windowsGfx` (по умолчанию выключена: проверен только на экране входа, см. память).
    Кодеки: без сжатия, `RfxProgressive` (полный: SIMPLE/FIRST/UPGRADE, режим extrapolate, тайлы-разности; состояние тайлов
    хранится внутри экземпляра, свой у каждой поверхности; сверен с FreeRDP и с реальным потоком Windows), `ClearCodec`
    (остаток, полосы с кэшем столбцов, глифы, подкодеки несжатый и RLEX; NSCodec и Planar не реализованы, CAVIDEO тоже —
    Windows их не присылал), H.264. Команды: SolidFill, SurfaceToSurface, кэш (при `SMALL_CACHE`).
    H.264 с аппаратным декодированием: `HardwareAvc.kt` (`MediaCodec` только с `isHardwareAccelerated`, вывод в буфер,
    `getOutputImage`; результат находит свои прямоугольники по номеру кадра в `presentationTimeUs`; интерфейсы
    `AvcDecoder`/`AvcDecoderFactory` — для подстановки в тестах), `AvcStream.kt` (`Avc420Stream`, `Avc444Stream` — разбор,
    `YuvConverter` — YUV 4:2:0 → ARGB по формулам FreeRDP: BT.709, полный диапазон). Прямоугольники потока считаются от угла
    поверхности, кадр H.264 — поверхность целиком, округлённая до 16. Предлагаемые возможности: GNOME с декодером — 8.0 и
    8.1 с AVC420 (версии 10+ без `AVC_DISABLED` обязывают понимать AVC444); без декодера — 8.0/8.1/10.0 с отключённым AVC;
    Windows (`classic`) — 8.0/8.1, с декодером ещё 10.3 с `AVC_THINCLIENT`. Факты о Windows (снято на экране входа): H.264
    она не принимает при 8.1 (подтверждённые флаги без AVC420), а при 10.3 присылает кодек 0xF (AVC444v2) с LC=1 — только
    основной вид, один поток Main-профиля, по кадру на команду; именно его и применяет `GfxChannel` (дополнительный вид
    при LC=0/2 пропускается — цветность упрощена до 4:2:0). Без AVC Windows шлёт Progressive и ClearCodec даже при версии 8.0.
    HEVC не реализован: в MS-RDPEGFX и FreeRDP его нет (ни идентификатора кодека, ни флага).
    Скорость: перевод YUV→ARGB построчный и многопоточный (`YuvConverter`), изменённые области уходят на экран без копирования
    (`RdpListener.onBitmapRegion`, `RemoteView.applyBitmap` с шагом строки); `MapSurfaceToOutput` ничего не рисует (иначе чёрный
    кадр затирает прежнюю картинку), нарисованное до монтирования копится и уходит после него. Раз в 5 с в журнал (тег RDP)
    пишется статистика: `gfx: за N с кадров …` (ожидание декодера, перевод в ARGB, вывод) и `декодер: …` (время кадра внутри
    `MediaCodec`) — по ней искать узкое место, а не гадать. Смена размера внутри сеанса (`onDesktopSize` → `initDesktop(live = true)`):
    Windows присылает новый размер за ~0,5 с, а кадры не замолкают, поэтому `RemoteView` убирает прежнюю картинку не позже
    `LIVE_SETTLE_MAX_MS` после покрытия стола (с переподключением по-прежнему ждёт затишья).
  - Байтовые структуры — `Bytes.kt` (`ByteWriter`/`ByteReader`). Раскладки PDU брались из исходников FreeRDP.
- **Экран сеанса** — `RemoteActivity.kt` (Compose-оболочка, панель инструментов, баннеры, жизненный цикл)
  и `RemoteView.kt` (отрисовка, касания). Экран сеанса поворачивается (`fullUser`, учитывает блокировку
  поворота): в книжной ориентации стол 1920 по высоте. При повороте с GFX — `RdpClient.resizeDesktop`,
  без GFX (Windows) — переподключение с новым размером (сеанс Windows сохраняется; события старого клиента
  отсекаются по `sessionSeq`). Кнопка «Повернуть» в панели сеанса (`rotateSession`, логика направлений и часы анимации — `SessionRotation.kt`) фиксирует `requestedOrientation`: из альбомной картинка идёт на 90° влево (поворот дисплея −1), из книжной обратно; работает при выключенном автоповороте, после возврата в альбомную при включённом автоповороте ориентация отдаётся системе. Смена ориентации (любая, не только кнопкой) показывается анимацией в `RemoteView`: `beginRotation` (из `onConfigurationChanged`) снимает картинку стола, она поворачивается и растягивается под новое окно, мутнеет (`RenderNode` + `RenderEffect`) и держится, пока Windows не ответит новым размером (`initDesktop` заливает новый стол прежней картинкой, готовность — по покрытию кадрами, иначе по таймауту), затем плавно исчезает; системная анимация поворота отключена (`ROTATION_ANIMATION_JUMPCUT`), переподключение без GFX идёт без окна «Подключение…» (`quietReconnect`). Прежняя картинка уходит, когда кадры нового стола покрыли половину площади и замолчали на 0,5 с (экран входа и «Добро пожаловать» после переподключения анимируются и ждут своего конца; не дольше 5 с после первого кадра), живой стол рисуется только под исчезающей картинкой; `settleOrientation(afterReady = true)` не завершает анимацию (размер после переподключения совпадает с запрошенным). Пока Windows отвечает, поверх картинки крутится лоадер (`RemoteView.onRotationWait` → `rotationWait`). Угол старта — кратчайший путь (поворот дисплея на 3 = −1 четверть). Кнопка «Настройки» в панели сеанса открывает `SessionSettings`: только то, что
  действует на лету (сила скролла/инерции, скорость мыши и её колёсика (`Device.mouseWheelPercent`) и прокрутки пером (`Device.stylusScrollPercent`, множитель поверх силы скролла пальцами,
  `RemoteView.setStylusScrollSpeed`; колёсико — множитель на
  `AXIS_VSCROLL` в `RemoteView.mouseWheel`) — `applyInputLevels`, сохраняются через
  `DeviceRepository.update`, который не пишет сеансовые пароли; все пять ползунков — проценты 50–200 с шагом 10
  (`Device.*Percent`, `StrengthLevels.snap`); «100%» у инерции и мыши — настроенные значения владельца
  (`StrengthLevels.inertiaFactor`/`mouseFactor`, в движок идёт именно они, а не `factor`), при смене опорной
  величины поднять `SCALE_VERSION` и добавить шаг в `DeviceRepository.migrateLevels` (старые уровни 1–9 → проценты); захват жестов; микрофон; кнопки «Калибровка», «Файлы на ПК», «Папка на ПК» — их нет в панели сеанса) — новую живую настройку
  добавлять туда, а требующую переподключения (масштаб, глубина цвета, диск) остаётся в форме ПК. Масштаб Windows
  (`Device.scalePercent`, Client Core Data и DisplayControl) сервер применяет только к новому сеансу: к сохранённому
  сеансу пользователя (один на пользователя, создан на физическом мониторе) подключение масштаб не меняет — проверено на
  ПК, DisplayControl с тем же размером тоже не помогает; в форме ПК это сказано в подсказке. Выход из сеанса
  (`leaveSession`) при `isTaskRoot` (сеанс открыт с ПК или из уведомления) сперва открывает `MainActivity`, иначе
  `finish()` сворачивал бы приложение; закрывать экран сеанса через `finish()` напрямую не надо. Windows без GFX по DisplayControl меняет размер у себя, но не сообщает его клиенту. Ввод: `TouchpadEngine` (захват указателя), `TouchpadGestures`,
  `TouchscreenGestures`, `ScrollFling`, `KeyCaptureService` (служба спец. возможностей для Win/Alt+Tab).
  Смартфон: захват указателя и калибровка тачпада не включаются (нет чехла-тачпада —
  `RemoteActivity.fingerInput()` по `smallestScreenWidthDp < 600`), ширина плашек считается
  `panelWidth(phone, …)`, а не фиксированными 520/560 dp. **Панель сеанса — одна компактная `SessionToolbar` для обоих
  форм-факторов**: таблетка с иконками без подписей (клавиатура, микрофон, камера, Win, «⋮») и отдельная красная кнопка
  «Отключиться»; всё остальное (настройки, поворот, жесты, Ctrl+Alt+Del, Alt+Tab только на телефоне, агент) — в выпадающем
  меню `SessionMenu`. На планшете она сверху, свёрнута в «ручку» и сама сворачивается через 5 с (переключатели клавиатуры,
  микрофона, камеры и открытое меню таймер продлевают), на телефоне всегда внизу над клавиатурой. **Правило пользователя: каждая новая настройка
  подключения, которую можно менять прямо во время сеанса, обязательно получает кнопку в таблетке** (а не только пункт меню или
  переключатель в `SessionSettings`; ползунки и прочее, что в таблетку не уложить, — исключение, но и тогда рядом нужна кнопка/вход
  в них); пункт меню «⋮» — для действий, не являющихся настройками (Ctrl+Alt+Del, поворот и т. п.). Кнопки таблетки — список `BarAction`
  (`rank` — важность, `menuLabel` — подпись в меню): на узком экране, где ряд вместе с «⋮» и «Отключиться» шире окна (телефон
  при полном наборе: клавиатура, микрофон, камера, геолокация, Win, обновление агента), лишние по `rank` уходят первыми пунктами
  в «⋮», а не за край экрана; новая кнопка таблетки обязана быть `BarAction`. Экранная клавиатура имеет три режима `KeyboardMode` (показана / скрыта / автоматически; кнопка
  таблетки (`cycleKeyboardMode`) переключает их по кругу; если клавиатуру Windows в режиме «показана» закрыли на ПК (`tkb` с `visible: false` при открытом приложении), режим сам становится «скрыта»; режим запоминается для каждого ПК в prefs `ui`, ключ
  `kbd_mode_<id ПК>`, по умолчанию автоматически; «назад» при показанной клавиатуре переводит `показана` в `скрыта`).
  Клавиатуру показывает **Windows на ПК** (сенсорная клавиатура TabTip в потоке RDP): режим уходит агенту в поле `kbmode`
  сообщения `keyboard` (`AgentLink.setKeyboardMode`), агент (`TouchKeyboard.Mode`, 1.9.1+, `KeyboardMode.AGENT_VERSION`) показывает
  клавиатуру сразу и держит (`show`), прячет (`hide`) или показывает по щелчку в поле ввода без физической клавиатуры (`auto`).
  Клавиатура Android — запасной путь без агента нужной версии (Ubuntu, агент старше): `RemoteActivity.applyKeyboardMode`; если она
  нужна, режим «показана» открывает её. Механика клавиатуры Android: у `RemoteView` нет
  `InputConnection`, поэтому крошечный `EditText` (`ensureImeEdit`) в окне поднимает системную клавиатуру,
  а её `KeyEvent` разбирает `forwardImeKey` (символы — скан-кодом через `ScanCodes.forChar` либо
  Unicode-событиями RDP, модификаторы держатся вручную); служба перехвата клавиш вызывает тот же
  `handleKeyEvent`. Кнопки мыши «средняя», «назад», «вперёд» Samsung обрабатывает на уровне ОС по своим настройкам
  (`Settings.System mouse_middle_button_option`, в `dumpsys input` — `Mouse button behavior(S/T/B/F)`) и может отдать как
  Home/«Недавние», Back, Forward: приложение сворачивается или сеанс закрывается. `RemoteActivity.mouseButtonAsKey` узнаёт
  такое событие (скан-код BTN_MIDDLE/SIDE/EXTRA/FORWARD/BACK 0x112–0x116 или клавиша без скан-кода от источника «мышь»)
  и шлёт на ПК кнопку через `RemoteView.mouseButtonKey`: средняя — `PTR_MIDDLE`, «назад»/«вперёд» — боковые кнопки
  `RdpClient.sendMouseX` (TS_POINTERX_EVENT, `PTRX_BACK`/`PTRX_FORWARD`; те же кнопки из `MotionEvent.buttonState` идут
  через `applyButtons`). Перехват работает только через службу перехвата клавиш; события пишутся в журнал `Input`.
  На планшете эти кнопки дополнительно доходят до приложения обычными событиями мыши (`buttonState`), а ОС всё равно
  выполняет своё действие (сворачивает, «назад») — его перехватом не отменить. Отключаются они только настройками Samsung
  в `Settings.System`: `mouse_middle_button_option` = 3 (обычный щелчок), `mouse_additional_1_option` и
  `mouse_additional_2_option` = 0 (нет действия); без записи у боковых действует системное «назад»/«вперёд». Приложение
  записать эти ключи не может (провайдер настроек отвечает `IllegalArgumentException: You cannot keep your settings in the
  secure settings` даже при `WRITE_SETTINGS`; пишет только оболочка adb: `settings put system <ключ> <значение>`), поэтому
  пункт «Кнопки мыши» в окне прав (`AppPermission.MOUSE_BUTTONS`, только Samsung) лишь читает их и показывает шаги ручной
  настройки (`howTo`).
  **Перо Samsung (S Pen)**: события `TOOL_TYPE_STYLUS`/`ERASER` обрабатывает `StylusEngine` (чистая логика под тестами;
  `RemoteView.stylusHover`/`stylusTouch` — обвязка), а не пальцевый `fingerTouch`. Наведение водит курсор, кнопка пера
  (`BUTTON_STYLUS_PRIMARY` или `BUTTON_SECONDARY`) — правая кнопка мыши (`applyButtons`; при подъёме пера с нажатой кнопкой
  `stylusButtonLatched` не даёт повторного нажатия). Касание: без движения — щелчок; движение — по форме курсора Windows
  (`CursorKind`, поле `kind` сообщения `cursor` агента 1.9.4+; без агента и для Ubuntu всегда стрелка): «I» (`TEXT`) —
  выделение, размер/перемещение/перекрестие (`DRAG`) — перетаскивание, остальное — прокрутка по обеим осям с инерцией;
  придержанное на месте перо (`LONG_PRESS_MS`) перед движением перетаскивает при любом курсоре. Решение — по выходу за
  `STYLUS_SLOP_DP`, левая кнопка нажимается в точке касания. Курсор Windows при пере рисуется самим `RemoteView`
  (`penInput`), системный указатель пера скрыт (`onResolvePointerIcon`). Новый вид курсора, меняющий поведение пера, —
  в `CursorKind` и в `CursorWatcher.Kind`.
  **Нативное касание Windows (RDPEI, MS-RDPEI)**: `Device.nativeTouch` (`Boolean?`, json `native_touch`; null — «Авто», по умолчанию и остаётся null: нативное, когда канал открыт, иначе мышь; явное true/false ставит форма ПК или переключатель в сеансе).
  Канал `rdp/RdpeiChannel.kt` (DVC `Microsoft::Windows::RDS::Input`, объявляется для любой Windows при `RdpConfig.touch`; сжатые
  целые `RdpeiInts`, рукопожатие SC_READY→CS_READY, кадры касаний `0x0003` и пера `0x0008`, SUSPEND/RESUME) открывает сама Windows;
  `RdpClient.touchReady`/`penReady`, `sendTouch`/`sendPen` (через очередь ввода), `RdpListener.onTouchChannel`. Чистая логика —
  `NativeTouchEngine` (контакты 0…9, отпуск обязателен, `cancelAll` шлёт `UP|CANCELED`, у пера своя машина наведение/касание/уход;
  `keepAlive` повторяет неподвижные контакты `UPDATE`-кадрами каждые `RemoteView.NATIVE_KEEPALIVE_MS` = 20 мс — Android неподвижный палец
  не сообщает, а без кадров Windows ведёт удержание хуже: опыт с `InjectTouchInput` на ПК — повтор клавиши TabTip 3 символа за 1,5 с против 39);
  `RemoteView` при `setNativeTouch(true)` и готовом канале отдаёт пальцы (`nativeFingerTouch`) и перо (`nativePenEvent`) Windows целиком,
  без `TouchscreenGestures`/`StylusEngine`/кнопки мыши; путь жеста выбирается на `ACTION_DOWN` (`nativeGesture`), при смене режима и
  потере фокуса контакты отменяются. Перо идёт нативно, только если сервер объявил multipen (`penReady`), иначе остаётся `StylusEngine`.
  `RemoteActivity.onTouchChannel`: при `nativeTouch == null` режим уже включён (`nativeTouchOn`), выбор не перезаписывается, один раз показывается подсказка; переключатель — пункт
  меню «Касание» и `SessionSettings`, форма ПК — «Касание экрана» (Авто/Нативное/Мышь); если канал не открыт, работает мышь.
  Перо в нативном режиме — `Device.stylusMode` (`StylusMode`, json `stylus_mode`, форма ПК и `SessionSettings`, меняется на лету через
  `RemoteView.setStylusMode`): `MOUSE` — `StylusEngine`, `TOUCH` — перо идёт тем же путём, что палец (`nativeFingerTouch`, номера контактов
  со сдвигом `stylusContactOffset`, без наведения/нажима/кнопки), `PEN` (по умолчанию) — настоящее перо RDPEI, если сервер объявил multipen. Без
  нативного режима перо всегда `StylusEngine`.
  **На экране блокировки Windows кадры RDPEI не применяет** (канал открыт, кадры уходят, но касания оживают только с разблокировкой —
  по журналам ПК: Kernel-Power 566 `SessionUnlock`, после сна и закрытой крышки), а мышь работает. Поэтому `status` агента с
  `state: locked` (`RemoteActivity.setRemoteLocked` → `RemoteView.setRemoteLocked`) временно переводит пальцы и перо на мышь
  (`nativeAllowed()`), разблокировка возвращает нативный ввод; без агента это не определяется. **После сна ПК** (и без блокировки)
  Windows не применяет касания нового подключения, пока не придёт ввод мышью (журналы 24.11 07:16: касания ожили сразу после щелчков
  в режиме «мышь»), поэтому `RemoteView.primeNativeInput` перед первым нативным касанием каждого `RdpClient` сдвигает курсор в точку
  касания (два `PTR_MOVE`, в журнале `rdpei: перед первым касанием курсор сдвинут…`).

  (`rdpei: → касание/перо №N`, первые пять пакетов и каждый 500-й; `…не отправлено` — канал приостановлен): по нему видно, уходит ли
  ввод. Перо в нативном режиме: `PenPoint` несёт нажим и наклон (`PenTilt.fromAndroid`: `AXIS_TILT` + `AXIS_ORIENTATION` → TILTX/TILTY,

  **Кнопка пера** (`Device.stylusButton`, `StylusButtonAction`, форма ПК и `SessionSettings`, одинаково в режимах мыши и нативного
  пера): правая кнопка (в нативном — признак кнопки пера), ластик (только нативное перо; в режиме мыши как правая), средняя кнопка,

  (идентификатор `<id ПК>|<id папки>|<путь>`, `ListingCache`, `ReadWindow`), `agent/FilesAccess.kt` (состояние кнопки и `PcRoots`),
  `agent/PcFilesLauncher.kt` (значок папки на `DeviceCard` открывает «Файлы» на диске ПК; подсказки неактивного значка — `ButtonHints.files`).
  Копирование и перемещение внутри ПК флагами не объявлены — система делает их чтением и записью через планшет. Новую файловую операцию
  добавлять в `FileService` (с проверкой `share.Write` для изменяющих), `PcFiles`, провайдер и тесты обеих сторон; шифрование и подпись
  сверять с .NET-агентом эталонными значениями (см. `PcFilesTest`).
- **Состояние ПК и пробуждение**: агент (`PcStatus.cs`) шлёт `status` (блокировка, кто в сеансе, простой, уход в
  сон/гибернацию/выключение/перезагрузку/выход, MAC для WoL) и по LAN, и по DVC. Планшет хранит последнее
  сообщение (`data/PcStateStore.kt`), состояние карточки выводит `PcStatusRules` (`data/PcStatus.kt`) из него,
  связи с агентом и проверки порта RDP. Подключение к недоступному ПК с известным MAC (`Device.wakeMac`) сначала
  будит его (`data/WakeOnLan.kt`: UDP 9 и 7 на 255.255.255.255, широковещательные адреса подсетей и адрес ПК),
  затем ждёт порт RDP (`RemoteActivity.connectWaking`).
- **Восстановление после обрыва связи**: `RdpListener.onClosed(error, lost)`; `lost` ставит `RdpClient.isConnectionLoss` — транспортная
  ошибка (`IOException`) без `errorInfo` от сервера и не на этапе CredSSP (сброс там — отказ по паролю, его повторять нельзя: блокировка
  учётки). Если сеанс уже был подключён (`everConnected`), `RemoteActivity.scheduleReconnect` сам подключается заново (паузы
  `RECONNECT_DELAYS_MS`, окно `RECONNECT_WINDOW_MS` = 5 мин, потом обычная ошибка с «Повторить»); последняя картинка остаётся под
  плашкой «Связь потеряна… попытка N», `SessionService` не останавливается, «Отмена»/`disconnect` обрывает попытки. Решения сервера
  (выход из системы, другой пользователь, администратор, простой), закрытие пользователем и команды питания не восстанавливаются.
  Восстановление идёт простым `connect()`, без Wake-on-LAN (иначе ПК, ушедший в сон, будился бы сам). Тихий обрыв сокета замечает
  `RdpClient.tuneKeepAlive` (TCP keepalive 15 с/5 с/3 зонда + `TCP_USER_TIMEOUT` 35 с): чтение без таймаута, стол может молчать.
- **Микрофон планшета в сеансе Windows**: настройка `Device.microphone` (по умолчанию выключена) плюс кнопка
  «Микрофон» в меню сеанса; разрешение `RECORD_AUDIO` спрашивается при первом включении. Захват — `MicSource.kt`
  (`AudioRecord`, 16 бит, 40 мс блоки; источник `VOICE_COMMUNICATION` + системные `AcousticEchoCanceler`/`NoiseSuppressor` — иначе при видеозвонке микрофон слышит звук ПК из динамиков планшета и собеседник слышит эхо; в журнале `mic: … обработка: …`), протокол — `rdp/AudinChannel.kt` (DVC `AUDIO_INPUT`, MS-RDPEAI: версия 2,
  только PCM 16 бит из списка сервера, `DATA_INCOMING` перед каждым `DATA`). Client Info шлёт `INFO_AUDIOCAPTURE`
  (0x200000), иначе Windows не создаёт устройство записи. Windows открывает канал `AUDIO_INPUT` только на время
  записи в программе на ПК, поэтому включение микрофона «взводится» (`RdpClient.micArmed`) и срабатывает на очередной
  OPEN; при включённой настройке и выданном разрешении микрофон взводится сам при старте сеанса, кнопка его выключает.
  При закрытии сеанса захват останавливается. Для Ubuntu канал не включается.
- **Камера планшета в программах Windows**: настройка `Device.camera` (по умолчанию выключена, диалог
  в `ui/Dialogs.kt`); разрешение `CAMERA` спрашивается один раз при входе в сеанс, если настройка включена —
  канал объявляется только при подключении, поэтому разрешение, выданное во время сеанса, требует
  переподключения (`RemoteActivity.askCameraPermission`/`requestCamera`). Захват — `CameraSource.kt`
  (Camera2; `YUV_420_888` → NV12, для MJPG сжатие в JPEG через `YuvImage`). Каждый объектив — **отдельное устройство
  Windows** («Планшет: тыльная», «… (ультраширокая)», «… (телеобъектив)», «Планшет: фронтальная»…): переключение
  делается средствами программы на ПК (кнопка «Сменить камеру», список камер в браузере/Teams). Тип объектива —
  по эквиваленту фокусного расстояния (≤20 мм ультраширокий, >45 мм теле), одинаковые дубли стороны отбрасываются,
  датчики глубины и ИК отфильтрованы по `BACKWARD_COMPATIBLE`; логическая камера с зумом ≤0.7× даёт ультраширокий
  как зум до минимума. Поворот кадра: базовый по формуле Camera2 для альбомного положения планшета
  (`CameraSource.DISPLAY_ROTATION` = 270°: тыльная `SENSOR − 270`, фронтальная `SENSOR + 270`; на Tab S9 Ultra у всех 180°)
  плюс дополнительный из настроек ПК (`Device.cameraRotation`, кнопки 0/90/180/270° по часовой стрелке); при итоговых 90/270°
  снимается альбомный кадр, поворачивается (`Nv12.rotate`) и Windows предлагается книжный 720×1280 (`EcamCamera.rotation`).
  Какие камеры показывать Windows — `Device.cameraOff` (идентификаторы из `CameraSource.catalog()`; отключённые не
  попадают в `devices()`); обе настройки лежат на вкладке «Устройства» формы ПК (значения по умолчанию) и дублируются в окне настроек сеанса: там и кнопка «Камера» в меню
  сеанса меняют набор камер на лету (`CameraSource.configure` + `RdpClient.refreshCameras` → `EcamEnumerator.refresh` шлёт Windows
  `DeviceAddedNotification`/`DeviceRemovedNotification`; каналы устройств названы по номеру в `catalog()`, поэтому имена не сдвигаются).
  Живое добавление/удаление устройств проверено только юнит-тестами; поворот применяется, когда программа на ПК заново откроет камеру.
  Одновременно снимает одна камера, `stop(id)` гасит только свою. Протокол —
  `rdp/EcamChannel.kt` (`EcamEnumerator` на DVC `RDCamera_Device_Enumerator` анонсирует все камеры, затем `EcamDevice`
  на каналах `Camera<i>`; MS-RDPECAM версия 2, объявляется один формат — MJPG 1280×720 с флагом DecodingRequired
  (проверено на ПК только с ним; сырой NV12 и другие размеры на рабочей схеме каналов не пробовались).
  **Windows открывает канал устройства 2–4 раза одновременно** (свойства, запуск потока, запросы кадров): состояние
  потока общее (`EcamShared`), а ответ и кадр уходят в тот канал, откуда пришёл запрос; `Deactivate` с чужого канала
  поток не останавливает. Кадр отдаётся в ответ на `SampleRequest` — лишние кадры не шлются). Поток идёт, только когда программа
  на ПК открыла камеру (`EcamDevice` зовёт `onActive`, `RemoteActivity` показывает значок «Камера: ПК
  смотрит»); сам поток, как у настоящей веб-камеры, запускает приложение на ПК; кнопка «Камера» лишь показывает камеры Windows или убирает их.
  Для Ubuntu канал не включается.
- **Геолокация планшета в Windows**: настройка `Device.location` (json `loc`, по умолчанию выключена; вкладка «Устройства и файлы» формы
  ПК, только Windows, применяется при подключении) плюс кнопка «Геолокация» в таблетке панели сеанса (видна у любого Windows; при выключенной
  настройке нажатие включает её для этого ПК, спрашивает разрешение и тихо переподключает сеанс) и переключатель в `SessionSettings` (при включённой настройке). Протокол — `rdp/LocationChannel.kt` (MS-RDPEL, DVC `Microsoft::Windows::RDS::Location`:
  `SERVER_READY` → `CLIENT_READY` (версия 2.0, если её назвал сервер; флаги 0), затем `BASE_LOCATION3D` на каждое определение — дельты не
  используются; `LocationNumbers` — FOUR_BYTE_FLOAT/SIGNED_INTEGER, сверены с `encoded_types.c` FreeRDP; скорость м/с, курс, точность м, источник
  GNSS/Wi-Fi). Канал открывает Windows; `RdpClient.setLocation` «взводит» передачу до его открытия (как микрофон), `CLIENT_READY` и запуск
  датчиков происходят только при включённой передаче. Источник — `TabletLocation.kt` (`LocationManager` без Google Play Services: GPS, сетевой и
  fused, лучшее определение по `LocationPick`, отдельный поток, повтор последнего раз в 30 с; в канал ничего не пишется из потока интерфейса). Разрешение
  `ACCESS_FINE/COARSE_LOCATION` (`AppPermission.LOCATION`) спрашивается при первом нажатии кнопки; при выданном — передача взводится сама при старте
  сеанса. Служба сеанса получает тип `location` (`SessionService.start(…, location = true)`, повторный вызов при переключении посреди сеанса),
  иначе Android не отдаёт координаты свёрнутому приложению; без выданного права тип не добавляется (иначе `SecurityException`). Кнопка не горит
  «передаётся», пока Windows не открыла канал (`RdpListener.onLocationActive`). Для Ubuntu канал не включается.
- **Защита RDP** (Windows, агент 1.8+; RDP на ПК может быть открыт в интернет): агент следит за журналами
  Windows, читаемыми без администратора, — `RdpCoreTS/Operational` (событие 140: неверный пароль, с адресом) и
  `TerminalServices-LocalSessionManager/Operational` (21/25 вход, 23 выход, 24 отключение); журнал «Безопасность»
  без администратора недоступен. Файлы агента: `GuardRules.cs` (адреса/подсети `IpTools`, белый список `Whitelist`, настройки `GuardSettings` и правила
  `ThreatDetector` — чистая логика без интерфейса), `Guard.cs` (`RdpEventSource`, `ConnectionGuard`: история при запуске, журнал и угрозы
  в `%LOCALAPPDATA%\HiWebAgent\guard.json`, команды), `Firewall.cs` (правила брандмауэра), `GuardHelper.cs` (помощник блокировки: клиент, установка, служба),
  `GuardForm.cs` (окно и `GuardText`). Угрозы: `bruteforce` (3 неудачи за 10 мин с подсети /24) и `unknown_logon` (вход, после которого планшет
  не открыл канал за 30 с; открыл — адрес запоминается в белом списке, в истории — по `channel opened` из `agent.log`).
  **Белый список и режим** (агент 1.9.5+, `GuardSettings`: `Mode` normal/whitelist, `AutoLearn`, `LearnSubnet`): адреса и подсети
  `WhitelistEntry` (ручные и автоматические) не проверяются и не блокируются; в режиме whitelist любая неудача с адреса вне списка —
  угроза `unlisted` (при пороге — `bruteforce`), вход планшета без автозанесения — `new_address`. Открытая угроза по той же подсети
  обновляется на месте, а не плодится (`ConnectionGuard.AddThreats`). Подсеть, пересекающуюся со списком, блокировать нельзя. Команды
  планшета `trust` (ip/cidr), `untrust`, `settings`; приложение: `GuardState.mode == null` — агент старше, настройки скрыты.
  Блокировки «всё, кроме белого списка» через брандмауэр нет: автозанесение и блокировка исключают друг друга (адрес вне списка не
  дойдёт до входа), а ошибка отрезала бы владельца, который сидит на RDP из интернета, — режим только предупреждает.
  **Автоблокировка и помощник** (агент 1.10+; `GuardSettings.AutoBan` по умолчанию включена, `BanAfter` = 5, 2–50; пишутся в `guard.json`):
  `ThreatDetector.Describe` считает неудачи по подсети за `BanWindowMs` (час; тревога `bruteforce` — по-прежнему 3 за 10 минут),
  `ConnectionGuard.NoteFail/StartBan/FinishBan` просят заблокировать подсеть (`OfferedBlock`) у **помощника** (`GuardHelper.cs`) — службы
  `HiWebAgentGuard` от SYSTEM из копии exe в `%ProgramFiles%\HiWeb Agent` (ставится одним UAC: `--guard-fw install-helper --sid …
  [--enable-fw]`, снимается `remove-helper` и при удалении агента, `Installer.Uninstall`). Без помощника автоблокировка не может ничего —
  UAC-запрос из фона на ПК, где владельца нет, смысла не имеет (так решил пользователь). Канал `\\.\pipe\HiWebAgentGuard`: ACL —
  SYSTEM/администраторы/SID установившего, сеть запрещена; протокол и допустимые подсети (только публичные /24, IPv6 /64 и уже) —
  `HelperProtocol` в `GuardRules.cs` (чистая логика под `tests\test.cmd`). `PipeOptions.FirstPipeInstance` в .NET 4.x не работает
  (`ArgumentException`, канал не создаётся) — не возвращать. Ручные `Block/Unblock` идут через помощника, а без него — через UAC.
  Устройствам рассылаются `guard_fail` (на каждую живую неудачу, с одной подсети не чаще 0,5 с) и `guard_ban` (успех и неудача
  автоблокировки, ручная блокировка); на планшете — `GuardHub` (отсев дублей по `id` из двух каналов — `RecentIds`),
  `GuardNotifications.postFail/postBan` (канал `pc_guard_fail` отдельный, уведомление одной подсети заменяется), настройки —
  карточка «Автоблокировка» в `GuardDialog`, у агента — вкладка «Заблокировано» окна защиты. Проверка без UAC: службу можно поднять
  в тестовом процессе через `OnStart` (рефлексия), поддельный помощник — сервер на том же канале; реальные `sc create`/COM-правила
  без UAC не проверить.
  Блокировка — правило входящего трафика брандмауэра группы «HiWeb Agent»; менять брандмауэр без администратора
  нельзя, поэтому агент запускает свой exe с `--guard-fw …` через `runas` (UAC на ПК, `Program.Main` обрабатывает ключ
  первым делом). Выключенный брандмауэр правил не применяет: на ПК он может быть выключен,
  поэтому блокировка предлагает включить его (`enableFw`, с явным согласием в окне). Android-сторона: `agent/GuardHub`
  (приём `guard_state`/`conn`/`threat`/`guard_result` по LAN из `AgentHub` и из сеанса через `AgentLink`, команды
  `block`/`unblock`/`trust`/`dismiss`), `agent/GuardNotifications` (+ `GuardActionReceiver`: кнопки в уведомлении),
  `data/GuardLog` (чистое слияние и тексты — под юнит-тестами), `data/GuardStore` (хранение по ПК, `GuardNavigation`),
  `ui/GuardDialog` (значок щита на карточке ПК). Протокол — `windows-agent/PROTOCOL.md`.
- **Форма курсора Windows**: сервер по RDP присылает только стрелку (см. память `rdp-cursor`), поэтому агент
  (`CursorWatcher.cs`, сообщение `cursor`: PNG + точка привязки) сам следит за `GetCursorInfo` и шлёт курсор планшету;
  `AgentLink` разбирает его в `CursorImage`, `RemoteView.setAgentCursor` показывает его и не даёт серверной «стрелке
  по умолчанию» его перекрыть. Без агента (и для Ubuntu) остаётся то, что прислал сервер.
- **Сенсорная клавиатура Windows** (режимы показа — см. выше; прежние приложения без поля `kbmode` дают режим `auto`): планшет шлёт агенту `keyboard` (`physical` — по `Configuration.keyboard`/
  `hardKeyboardHidden` — учитывает и чехол, и Bluetooth; не по списку устройств: `sec_touchpad` чехла виден и без него); без клавиатуры агент
  (`TouchKeyboard.cs`: ловушка мыши + UI Automation + `ITipInvocation`) показывает TabTip при щелчке в поле ввода
  (UIA `Edit`/`Document` с системным курсором; программы с собственной отрисовкой текста — Scintilla/Notepad++ и
  Java AWT/Swing/IDE JetBrains — не отдают ни того, ни другого, поэтому узнаются по классу окна с фокусом,
  `IsSelfDrawnEditor`; диалоги и всплывающие окна Java `SunAwtDialog`/`SunAwtWindow` редактором не считаются; поле с ролью combobox —
  поиск google.com и т. п., UIA `ComboBox` — ввод, если его `ValuePattern` не только для чтения) и шлёт её прямоугольник (`tkb`). Нативные касания и перо RDPEI в ловушку мыши не попадают (по журналу агента
  на реальном ПК), поэтому в нативном режиме планшет сам шлёт `tap` с координатами стола (`NativeTapDetector`: один контакт, без сдвига,
  короче `LONG_PRESS_MS`; `RemoteView.onNativeTap` → `AgentLink.sendTap`, агент 1.11.1+ — `TouchKeyboard.Tap`); долгое касание внутри него на планшете — автоповтор клавиши, а не правая кнопка.
- **Уведомления Windows → планшет**: `NotificationWatcher.cs` опрашивает `UserNotificationListener` раз в секунду,
  `AgentApp.Forward` шлёт `notif` **только по каналу сеанса RDP** и только при свёрнутом приложении (`ForwardSkipReason`;
  по LAN без сеанса уведомления не идут). Каждое решение пишется в `agent.log` строкой `notif: <приложение> — …`
  (без текста уведомления). Объект слушателя привязан к потоку: опрос берёт свой `UserNotificationListener.Current` в
  своём потоке, иначе `GetAccessStatus` бросает `RPC_E_WRONG_THREAD`. Меню агента «Проверить пересылку уведомлений…»
  (`NotificationCheck.cs`: `NotificationCheckForm` + `ToastProbe`) показывает настоящий тост от имени Windows PowerShell
  и по шагам проверяет доступ, опрос, канал, свёрнутость приложения и ответ планшета `notif_ack` (`PcNotifications.blocker`:
  нет разрешения / выключен канал / приложение на экране). Для `Windows.Data.Xml.Dom` в `build.cmd` подключён `Windows.Data.winmd`.
  Иконка в карточке: агент (`AppIcons.cs`, оболочка `shell:AppsFolder\<AppUserModelId>` + `IShellItemImageFactory`, 128 px,
  только в памяти, вызывать из STA) кладёт PNG в `notif.icon`; планшет (`NotificationIcon.kt`) собирает из него большую иконку
  с цветным значком RemoteDesk в углу, без иконки приложения (системные уведомления) — один значок RemoteDesk. Маленькая
  иконка в статус-баре остаётся `ic_stat_pc`. `GetLogo` из API уведомлений для классических программ возвращает null.

## Сборка и тесты

- JDK нет в PATH: `export JAVA_HOME="/d/Program Files/Android/Android Studio/jbr"` перед `./gradlew.bat`.
- Юнит-тесты и APK: `./gradlew.bat --console=plain -q :app:testDebugUnitTest :app:assembleDebug`.

## Планшет и adb — осторожно

- adb: `%LOCALAPPDATA%\Android\Sdk\platform-tools\adb.exe`, планшет по беспроводному adb.
  Смартфон SM-S916B тоже по беспроводному adb (`adb mdns services` → `adb connect <ip>:<порт>`); при
  перезагрузке телефона или выключенном Wi-Fi он пропадает из списка устройств — тогда проверить `ping`.
- В приложении сохранён **настоящий ПК пользователя**: при открытом сеансе любой ввод через adb уходит на ПК.
  Перед `adb input` и перед `adb install -r` проверять `adb shell dumpsys window | grep mCurrentFocus`;
  если приложение на экране — не трогать, спросить пользователя.
- Не запускать `connectedAndroidTest` (удаляет приложение и сохранённые ПК). Ставить `adb install -r -t`.
- `am force-stop` выключает службу перехвата клавиш (`install -r` её сохраняет).
- Не вводить пароль пользователя самому; учётка Windows блокируется после 10 ошибок за 10 минут.
- **На этом ПК стоит настоящий HiWeb Agent пользователя** (привязан к планшету). Тестовый запуск exe из
  другой папки переустанавливает его; не трогать `HKCU\Software\HiWebAgent\Tablet` и не удалять агент
  без спроса. Команды питания на этом ПК не выполнять (только проверять доступность).
- Не добавлять и не удалять правила брандмауэра на этом ПК и не включать его без спроса (`guard-fw`, `Policy.Rules.Add`,
  `Set-NetFirewallProfile`): это настоящий ПК пользователя, а запрос UAC нельзя подтвердить из
  неинтерактивного сеанса. Читать правила и состояние брандмауэра, журналы Windows и `Get-NetTCPConnection` можно.
  Проверочную обвязку для `ConnectionGuard` собирать в scratchpad с каталогом данных во временной папке, а не в
  `%LOCALAPPDATA%\HiWebAgent` (там настоящие `guard.json` и `agent.log` работающего агента).
